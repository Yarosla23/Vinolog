# Архитектура Vinolog

## Границы системы

```text
Мобильный браузер
      │ multipart/form-data
      ▼
Nuxt server API ───────► Retrieval API (FastAPI, следующий этап)
      │                         │
      │                         ├─ нормализация / encoder / OCR
      │                         └─ candidate search / reranking
      ▼
Каталог и продуктовые ответы ◄── PostgreSQL + pgvector
```

- `apps/web/app` отвечает за интерфейс и состояние пользовательского сценария.
- `apps/web/server/api` валидирует HTTP-ввод и переводит результат внешнего сервиса в продуктовый контракт. CV-логика здесь не размещается.
- `packages/contracts` — единственный источник форм ответов между слоями.
- `services/retrieval` будет содержать поиск конкретного `slug`; он не должен знать о компонентах Nuxt.

## Два контракта поиска

Продуктовый маршрут возвращает `matched`, `uncertain` или `not_found`, карточку, диагностические оценки и версии. Официальный оценочный маршрут будет добавлен только после получения скрипта организаторов и должен вернуть строго плоский JSON `{"slug":"..."}`. Оба маршрута обязаны использовать один результат ранжирования.

## Текущий поток

1. Пользователь выбирает фото через файловый input с `capture="environment"`.
2. Клиент проверяет тип и размер, создаёт локальный preview и отправляет `FormData` в `/api/scans`.
3. Nuxt server route повторно валидирует файл.
4. Пока `NUXT_PUBLIC_SCAN_MODE=mock`, маршрут возвращает маркированную демонстрационную карточку.
5. После подключения retrieval-сервиса Nuxt будет проксировать запрос через приватный `NUXT_RETRIEVAL_BASE_URL`.

## Инварианты

- Аналог не называется точным совпадением.
- `score` не называется вероятностью; `calibratedProbability` появляется только после калибровки.
- Инфраструктурная ошибка не превращается в `not_found`.
- Браузер не обращается к CV-сервису напрямую.
- Базовая карточка и локальные сохранения работают без LLM.
